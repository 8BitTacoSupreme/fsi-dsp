# Layer 02: mTLS + FIPS Hardening

## FSI Rationale

Confluent's upstream demo uses `autoGeneratedCerts` — self-signed, ephemeral certificates
with no CA trust chain and no client authentication. In FSI environments:

- **GLBA Safeguards Rule**: encryption of customer financial data in transit is mandatory
- **PCI-DSS 4.x § 4.2.1**: strong cryptography required for all data transmission; TLS 1.0
  and 1.1 explicitly prohibited
- **FFIEC IT Examination**: mutual authentication between components prevents broker
  impersonation and man-in-the-middle attacks inside the cluster network

**Failure mode without this layer:** unauthenticated broker access and cleartext interception
inside the Kubernetes overlay network — both are reportable control failures in a SOC 2 or
PCI audit.

## What this layer does

1. **Replaces `autoGeneratedCerts`** with named `secretRef` pointing to PEM cert+key+CA
   Secrets. Certs are minted by `ansible/roles/cp_mtls` or `LinuxOne/ansible-mtls/` on
   the target host (private keys never traverse the network — ADR-013 decision 2).

2. **Enables mTLS on internal listeners**: `listeners.internal.authentication.type: mtls`
   for broker-to-broker and component-to-broker communication. External listener retains
   Route edge-TLS for compatibility.

3. **FIPS mode**: `spec.tls.fips.enabled: true` on all component CRs. On s390x, this
   activates IBM Semeru's `IBMJCEPlusFIPS` provider and CPACF hardware acceleration for
   AES-GCM and SHA-2 operations.

4. **Cipher suite pinning**: `ssl.enabled.protocols=TLSv1.3,TLSv1.2` and an explicit
   FIPS-approved cipher suite list via `configOverrides.server`.

5. **cert-manager integration**: `certificate-crs.yaml` deploys cert-manager `Issuer` and
   `Certificate` CRs for declarative certificate auto-rotation (cert-manager Operator for
   OpenShift, s390x-compatible and FIPS-validated since v1.14.0).

## s390x FIPS caveat

**`spec.tls.fips.enabled: true` only takes effect on an OCP cluster installed in FIPS mode.**
Setting this field on a non-FIPS cluster is a no-op — the JDK will not load FIPS providers.

FIPS must be enabled at OCP install time via `fips: true` in `install-config.yaml`.
Post-install enablement is not supported by Red Hat. See `KNOWN-GAPS.md`.

For s390x specifically, FIPS validation runs through IBM Semeru 17's `IBMJCEPlusFIPS`
provider, which maps to CPACF hardware instructions (KIMD, KM, KMO) — see ADR-013
for the full s390x cryptographic stack decision.

## Manual cert rotation (no cert-manager fallback)

If cert-manager is not available:

```bash
# 1. Mint replacement cert (runs on the target OCP worker node, not the controller)
cfssl gencert \
  -ca=ca.pem -ca-key=ca-key.pem \
  -config=cfssl-config.json \
  -profile=server \
  kafka-csr.json | cfssljson -bare kafka

# 2. Update the K8s Secret
oc create secret generic kafka-tls -n confluent \
  --from-file=tls.crt=kafka.pem \
  --from-file=tls.key=kafka-key.pem \
  --from-file=ca.crt=ca.pem \
  --dry-run=client -o yaml | oc apply -f -

# 3. CFK detects the Secret update and triggers a rolling restart
oc get kafka kafka -n confluent -w
```

## Validation

```bash
bash layers/02-tls/validate-mtls.sh
```

Cluster-dependent. Asserts: no-cert client rejected; valid-cert client succeeds; TLS 1.0 rejected.
