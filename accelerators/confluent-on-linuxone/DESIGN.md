# Plan: Fork & FSI-harden Mondics's Confluent-on-LinuxONE runbook

## Context

`fsi-kafka-platform` is a GoodLabs accelerator repo for governed Kafka/Flink/SR
infrastructure across deployment models. It is at v3.0 (LinuxONE/s390x first-class),
with existing `scenarios/cfk-openshift-linuxone/` (Helm-values), Ansible roles
(`cp_rbac`, `cp_mtls`, `cfk_operator`, `cfk_topic`), ADR-013 (s390x guidance), and
observability templates for Splunk/Dynatrace.

IBM's Matt Mondics published a working public reference — Confluent Platform on
LinuxONE via the CFK operator on OpenShift, with Cluster Linking for x86→LinuxONE
migration (repo `mmondics/Confluent-LinuxONE-Mirror`, verified; article 2026-05-20).
His runbook is the **generic demo case**: CP 8.2.0, CFK 3.2.x, KRaft mode,
`platform.confluent.io/v1beta1` CRs, self-signed/`autoGeneratedCerts` TLS, **no RBAC,
no audit logging, Connect commented out**.

This work creates `accelerators/confluent-on-linuxone/` — a new top-level tier — that
preserves Mondics's runbook as a clean base and layers four FSI hardening controls on
top (RBAC, mTLS, Schema Registry governance, audit logging) as Kustomize Components,
so a reader sees the basic example and the enterprise-grade additions side by side.
Outcome: an FSI team can `flox activate`, follow the runbook, and deploy a
production-grade hardened CP on LinuxONE with each control independently validated.

## Decisions locked (from review)

1. **Upstream base = fetch-by-SHA.** `base/` ships a `fetch-upstream.sh` that
   `git clone --depth 1` + checks out a pinned commit SHA into `base/upstream/`
   (gitignored — never committed). No redistribution of unlicensed third-party code.
   `ATTRIBUTION.md` cites Mondics + the article; `KNOWN-GAPS.md` flags the
   network-access requirement.
2. **`auditor-readonly` = audit-topic-scoped.** Bound to `DeveloperRead` on
   `confluent-audit-log-events` + all SR subjects (metadata) + read-scoped cluster
   metadata. Explicitly **not** bound to `payments.*` business topics — true payload
   isolation, since Confluent `DeveloperRead` always grants consume.
3. **Reuse existing repo assets.** The accelerator's FSI overlays are Kustomize/CRD,
   but it wires in existing repo assets rather than duplicating them (see Reuse Map).

## Composition mechanism

Each `layers/NN-*/kustomization.yaml` is `kind: Component`
(`kustomize.config.k8s.io/v1alpha1`) — a non-buildable fragment carrying that layer's
`patches:` and `resources:`. `overlays/{dev,prod}/kustomization.yaml` is the single
buildable `kind: Kustomization`: `resources: [../../base]` + `components: [01-rbac,
02-tls, 03-schema-governance, 04-audit, 05-flink]`. Components apply in listed order,
encoding dependencies (RBAC's ConfluentServerAuthorizer before audit; TLS secrets before
MDS references them; 05-flink last because it depends on layer 01 MDS and layer 02's
`confluent-ca-issuer` ClusterIssuer). This gives each layer its own directory + README +
ownership boundary while keeping exactly one buildable artifact per environment.

Layer 05 is **resources-only** (no `patches:` block). Flink is a Kafka client — it adds
new CRs rather than patching existing ones. Per-overlay sizing (parallelism, checkpoint
interval, retention) is handled by patches in `overlays/{dev,prod}/kustomization.yaml`.

CFK CRs are not strategic-merge-annotated → Kustomize uses JSON-merge (list fields
replace, not append). Mitigation: each layer owns a **distinct CR field**
(`spec.authorization`, `spec.tls`, `spec.audit`); where two layers must both write
`configOverrides.server`, consolidate into one layer or use JSON6902 `add` patches.
Prefer first-class CR fields over raw `configOverrides` to keep patches non-colliding.

## Reuse Map (existing repo assets wired in)

| Accelerator concern | Reused existing asset |
|---|---|
| CFK operator install | `ansible/roles/cfk_operator` (readiness-gated) — RUNBOOK.md calls it instead of raw `helm install` |
| s390x base CR conventions | `scenarios/cfk-openshift-linuxone/values/kafka.yaml` node affinity / FIPS — sourced into TLS/RBAC patches |
| CA + cert PEMs feeding `spec.tls.secretRef` | `LinuxOne/ansible-mtls/` + `ansible/roles/cp_mtls` mint CA/leaf PEMs → become the K8s cert secrets; cert-manager is the in-cluster rotation alternative |
| RBAC drift reconciliation | `ansible/roles/cp_rbac` runs an optional LIST/DIFF/ADD/REMOVE audit pass over the declarative `ConfluentRolebinding` CRs (ops + CI) |
| SIEM dashboards/alerts | `observability/splunk/` + `observability/dynatrace/` — `layers/04-audit/siem/` references them, no duplication |
| s390x decision rationale | `docs/adr/013-linuxone-deployment-guidance.md` — cross-linked from layer READMEs |

CFK still manages all Confluent components; the Ansible roles act on the CFK-managed
cluster via MDS/Helm REST — no parallel broker management path.

## Layer detail

### 1. `layers/01-rbac/` — MDS RBAC
- Kafka CR patch: `spec.authorization.type: rbac`, `spec.services.mds` (TLS,
  `tokenKeyPair.secretRef`, `provider.type: ldap` with LDAP config block as the
  IdP boundary). SR/KsqlDB/KafkaRestProxy/ControlCenter patches add `dependencies.mds`.
- `ConfluentRolebinding` CRs map the 6 FSI roles to Confluent predefined roles:
  `platform-admin`→`SystemAdmin`; `topic-admin`→`ResourceOwner` Topic `PREFIXED`;
  `producer-only`→`DeveloperWrite`; `consumer-only`→`DeveloperRead` (Topic+Group
  `PREFIXED`); `schema-admin`→`ResourceOwner` Subject `PREFIXED` (`schemaRegistryClusterId`
  scope); `auditor-readonly`→`DeveloperRead` on `confluent-audit-log-events` + SR
  subjects only (see decision 2).
- Sample bindings for a `payments.` domain; bind to LDAP **groups** (`type: group`),
  never individuals — the IdP is the identity boundary.
- `secrets.template/`: `mds-token-keypair`, `ldap-credentials` with `<PLACEHOLDER>`.
- README: FSI rationale — segregation of duties, least privilege (SOX/FFIEC/PCI-DSS),
  failure mode = unbounded cluster admin. Validation: `confluent iam rbac
  role-binding list`; a `producer-only` principal attempting consume → expect 403.

### 2. `layers/02-tls/` — mTLS + FIPS
- Per-component patches replace `autoGeneratedCerts` with `spec.tls.secretRef`
  (PEM cert+key+CA secret); `listeners.internal.authentication.type: mtls` for
  broker/controller/SR/C3-to-broker mTLS; external listener keeps Route edge-TLS.
- `spec.tls.fips.enabled: true` on every component CR. `configOverrides.server`:
  `ssl.enabled.protocols=TLSv1.3,TLSv1.2`, FIPS-compatible `ssl.cipher.suites`.
- `certificate-crs.yaml`: cert-manager `Issuer`/`Certificate` CRs for declarative
  auto-rotation (cert-manager Operator for OpenShift is s390x-supported, FIPS-validated
  ≥1.14.0). Manual rotation runbook documented as the no-cert-manager fallback.
- `secrets.template/`: CA + per-component cert PEMs, all `<PLACEHOLDER>`.
- README: FSI rationale — encryption-in-transit + mutual auth (GLBA, PCI-DSS 4.x,
  FFIEC), failure mode = unauthenticated broker access / cleartext interception.
  Validation `validate-mtls.sh`: client with no cert → SSL handshake rejected;
  client with valid cert → `kafka-broker-api-versions` succeeds.
- s390x caveat: FIPS must be enabled at OCP install time — `spec.tls.fips.enabled`
  only takes effect on an already-FIPS cluster (→ KNOWN-GAPS + README).

### 3. `layers/03-schema-governance/` — Schema Registry governance
- SR CR patch: `configOverrides.server` sets `schema.compatibility.level=full_transitive`
  (prod) and subject-naming validation. `job-sr-bootstrap.yaml`: idempotent
  `restartPolicy: Never` Job issuing REST `PUT /config` (FULL_TRANSITIVE) and
  per-subject mode — the one sanctioned explicit bootstrap; PUTs are idempotent.
- Hard delete: not a single CR flag — controlled by withholding delete-capable roles
  (`ResourceOwner`) broadly + documenting the `?permanent=true` restriction; RBAC
  subject-prefix scoping from layer 01 is the real enforcement boundary.
- Subject naming regex is configurable per environment (overlay variable).
- README: FSI rationale — auditability of data contracts over time, regulatory
  replay; failure mode = silent breaking schema change / unrecoverable hard delete.
  Validation: bad subject name → rejected; incompatible change → FULL_TRANSITIVE
  rejects; hard-delete attempt by non-privileged principal → 403.

### 4. `layers/04-audit/` — Audit logging
- Kafka CR patch: `confluent.security.event.router.config` JSON routing auth
  attempts, authz decisions, and management events to `confluent-audit-log-events`.
  Depends on layer 01's ConfluentServerAuthorizer (component order).
- `kafkatopic-audit.yaml`: `KafkaTopic` CR pre-creating `confluent-audit-log-events`
  with `retentionMs` = 7y (`220752000000`) prod / 30d dev — overlay variable, so
  retention is declarative and authoritative (not left to broker auto-create).
- `connect-cr.yaml`: a `Connect` CR (upstream has Connect commented out) +
  `Connector` CRs — Splunk Sink (HEC) and a generic HTTP Sink → Dynatrace ingest API
  (no first-party Dynatrace connector — flagged in KNOWN-GAPS). Connector JARs are
  arch-neutral Java; baked into a custom s390x Connect image.
- `siem/` references `observability/splunk/` + `observability/dynatrace/`.
- README: documents captured events (authn attempts, authz decisions, schema changes,
  topic config changes, ACL/rolebinding changes); FSI rationale — immutable audit
  trail for OFAC/AML/SOX, 7y retention; failure mode = no forensic record of access.
  Validation `validate-audit.sh`: generate each event type, consume the audit topic,
  confirm each lands.

### 5. `layers/05-flink/` — Flink stream processing

- `FlinkEnvironment` CR: defines the CMF-managed Flink compute context. Specifies the
  s390x nodeAffinity block, RocksDB state backend, Prometheus metrics reporter (port 9249),
  and the mTLS cert volume mount for Flink→Kafka mutual TLS.
- `CMFRestClass` CR: defines the mTLS-secured CFK→CMF control channel. CFK uses this
  to submit, cancel, and savepoint FlinkApplications via CMF REST.
- `rolebindings/`: two self-contained ConfluentRolebinding CRs — `flink-developer`
  (LDAP group → FlinkEnvironmentAdmin) and three `flink-job-runtime-*` bindings
  (service account → DeveloperRead source, DeveloperWrite sink, DeveloperRead SR).
- `tls/certificate-crs.yaml`: cert-manager `Certificate` CRs for `cmf-tls` and
  `flink-kafka-client-tls`. Both `issuerRef` reference the EXISTING `confluent-ca-issuer`
  ClusterIssuer (registered by layer 02). No new PKI.
- `applications/`: two FlinkApplication CRs + SQL ConfigMaps. CFK ports of
  `reference/flink-sql/tumbling-window-aggregation.sql` and `stream-table-join-enrichment.sql`.
  SQL uses mutual TLS to Kafka (keystore + truststore) and `https://` SR URL (layer 02 mTLS'd SR).
- `topics/`: two KafkaTopic CRs for Flink sink output, `retention.ms=$(FLINK_OUTPUT_RETENTION_MS)`.
- `sql-runner/`: Dockerfile for the custom s390x cp-flink image (shipped, not built here).
  See KNOWN-GAPS.md G-12.
- Audit integration: Flink's Kafka access is audited automatically by layer 04 —
  the `ConfluentServerAuthorizer` (layer 01) fires on every Flink topic access and
  routes the event to `confluent-audit-log-events`. No layer-04 change required.
- Operator prerequisite: FKO + CMF Helm charts installed via `ansible/roles/flink_operators/`
  (RUNBOOK Step 1b). These operators are not Kustomize-managed — they are Helm-managed
  prerequisites, parallel to how `ansible/roles/cfk_operator/` manages the CFK operator.

- **RUNBOOK.md** — adapted wrapper, not a rewrite: walks deploy end-to-end, cites

- **MIGRATION.md** — wraps Mondics's Cluster Linking pattern (`base/clusterlink.yaml`)

  rollback procedure (re-point producers, demote mirror), post-migration evidence
  collection for regulatory review.
- **KNOWN-GAPS.md** — s390x register: fetch-by-SHA network requirement; FIPS-at-install
  constraint; no native Dynatrace connector (HTTP Sink workaround); verify Control
  Center next-gen s390x image; bootstrap-Job base image must be s390x (UBI9+curl);
  prefer Connect-based SIEM shipping over x86 node-agent sidecars (QEMU penalty).
- **README.md** — top-level: provenance table (IBM upstream vs GoodLabs additions),
  Mondics attribution + article cite, the four hardening layers with FSI rationale,
  build/validate instructions. Technical and dense, no marketing.

## Build & validation

- Build: `flox activate` → `base/fetch-upstream.sh` → `kustomize build
  accelerators/confluent-on-linuxone/overlays/prod`.
- Apply: `kustomize build overlays/prod | oc apply -f -` (server-side
  `--dry-run=server` first to exercise CFK CRD admission).
- Per-layer: run `validate-rbac.sh`, `validate-mtls.sh`,
  `validate-schema-governance.sh`, `validate-audit.sh`, `validate-flink.sh` — each confirms its control.
- End-to-end: deploy on an OCP-on-LinuxONE cluster, run all 4 validators, then
  exercise MIGRATION.md by cluster-linking to a second cluster and confirming
  mirror-lag → 0 + record-count parity.
- CI: add a `kustomize build` + CRD-schema lint job extending existing `ci/scripts`.
