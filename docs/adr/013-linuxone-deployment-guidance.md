# ADR-013: LinuxONE / s390x Deployment Guidance

**Status:** Accepted
**Date:** 2026-04-27
**Author:** Jeremy Hogan

> Renumbered from 009 on 2026-10-24 (collided with 009-linuxone-kafka-offload.md).

## Context

The FSI Kafka Platform supports six deployment models but has no first-class s390x / LinuxONE support. Financial institutions running IBM LinuxONE need certified deployment patterns for Confluent Platform on RHEL (s390x) and CFK on OpenShift (s390x), with particular attention to:

- JDK selection (IBM Semeru vs OpenJDK)
- Keystore format and FIPS compliance
- CEX hardware security module integration
- Cross-platform cipher suite compatibility

## Decision

### 1. Software keys by default, CEX optional

The `cp_mtls` role defaults to software-based PKCS12 keystores (`cp_mtls_keystore_backend: software`). CEX/PKCS#11 HSM support is available as an optional overlay (`cp_mtls_keystore_backend: pkcs11`) for customers requiring hardware-backed private keys. Rationale: software keys work everywhere, CEX requires specific hardware and configuration that varies by installation.

### 2. On-target keystore assembly

Private keys are generated and keystores assembled on the target host, never on the Ansible controller. This is critical for:
- FIPS compliance (keys must be generated in the FIPS boundary)
- Cross-JDK portability (keystores generated by IBM JDK load correctly on IBM JDK)
- Security (private keys never traverse the network)

### 3. PKCS12 only, not JKS or BCFKS

PKCS12 is the only keystore format used. JKS is deprecated. BCFKS (Bouncy Castle FIPS Keystore) is x86/OpenJDK-specific and not supported by IBM JDK's FIPS providers. On s390x with IBM Semeru, the FIPS-compliant path is PKCS12 with `IBMJCEPlusFIPS` provider.

### 4. IBM Semeru 17 as default JDK

IBM Semeru Runtime 17 (OpenJ9) is the recommended JDK for LinuxONE deployments. It provides:
- Native s390x optimization
- CPACF integration for hardware-accelerated crypto
- IBM FIPS providers (`IBMJCEPlusFIPS`, `IBMJCEFIPS`)
- Full Kafka compatibility

### 5. Cipher suite handling

Cipher suites are left at JDK defaults (empty `cp_mtls_ssl_cipher_suites`) unless the deployment involves cross-architecture clients (x86 clients connecting to s390x brokers). In cross-arch scenarios, operators should pin an explicit cipher suite list that both JDK vendors support.

### 6. CPACF is transparent

IBM CP Assist for Cryptographic Functions (CPACF) accelerates AES, SHA, and other operations at the hardware level without application changes. The platform documents CPACF detection as informational in FIPS validation but does not require it.

## Consequences

- LinuxONE becomes a first-class deployment model alongside CC, CFK, and CP-on-RHEL
- s390x-specific FIPS validation path added (IBM providers instead of Bouncy Castle)
- Documentation covers the full "Usual Suspects" checklist for s390x TLS debugging
- CEX integration is scoped but optional, reducing barrier to adoption

## Amendment 2026-10-24 — s390x FIPS

Confluent Platform FIPS mode is not yet supported on s390x (CP versions-interoperability,
"Linux on IBM Z (s390x) support", checked 2026-10-24). A tier whose policy requires FIPS 140
validated crypto on the brokers runs its brokers on x86/ARM until Confluent lists FIPS mode
for s390x. OS/JDK FIPS modes on s390x (RHEL `fips=1`, IBM Semeru `IBMJCEPlusFIPS`) are
outside Confluent's s390x support statement; this kit makes no claim that they work or break
with CP. mTLS, TLS 1.2/1.3 and CPACF acceleration are unaffected.

The decisions above are amended as follows; their text is left as written:

- **Context** ("Keystore format and FIPS compliance") and **Decision 2** ("FIPS compliance
  (keys must be generated in the FIPS boundary)"): no FIPS boundary applies on s390x.
  On-target key generation stands on its other two reasons, cross-JDK portability and
  keys never crossing the network.
- **Decision 3**: PKCS12 stands. "On s390x with IBM Semeru, the FIPS-compliant path is
  PKCS12 with `IBMJCEPlusFIPS` provider" is withdrawn.
- **Decision 4**: IBM's FIPS providers are no longer a reason to choose Semeru. Confluent's
  supported-JDK list (Temurin, OpenJDK, Zulu, Oracle) does not name Semeru; this amendment
  does not reverse the JDK decision.
- **Decision 6** and **Consequences** ("s390x-specific FIPS validation path added"): the
  s390x FIPS validation path is withdrawn; `scripts/validate-fips.sh` exits 3 (not
  applicable) on s390x.

The same support statement sets the s390x floor at CP 8.2.0, with a separately purchased IBM Z
software entitlement. See `docs/linuxone-fips-guide.md` and the accelerator's `KNOWN-GAPS.md` G-02.
